# Populating a new language into mapping_audit_*.db — STRICT RULES

These rules exist because the Arabic (`ar`) population run broke them twice
before landing correctly. Read this whole file before touching any
`mapping_audit_*.db` for a new language. **The rules below are not
suggestions — a run that violates any "MUST NOT" is a failed run, full
stop, even if it produces plausible-looking output.**

The reusable tool is `clone_en_to_language.py` in this folder. It already
implements every rule below. **Use it. Do not hand-roll a new script per
language, and do not "improve" the approach mid-run** — if it's wrong, fix
`clone_en_to_language.py` itself so every language benefits, then re-run.

---

## 0. The one-sentence version

For every `mapping_audit_*.db`, clone the exact `en` row set (same
`puzzle_slug`/`legacy_key`/`new_key` triples) into the new language, and
fill only the two value columns from that language's **real, current** prod
content — never regenerate rows from the new language's own structure,
never invent a value that isn't in prod, never touch anything outside the
target language's rows.

---

## 1. MUST clone `en`'s row set — MUST NOT re-derive rows from the target language

**What went wrong the first time:** puzzle-category rows were generated by
running the audit scripts fresh against Arabic content. This produced a
*different* row set than English's (missing the `collection.*` block and
`body.faqs` rows, which only exist when auditing an already-migrated
"converted" content file — and no such file exists yet for any non-English
locale). Row counts silently diverged from English (e.g. `cute`: en=1063
vs a fresh ar run=931) for a reason that had nothing to do with Arabic
content actually being incomplete.

**Rule:** Read every `en` row for the db (`puzzle_slug`, `legacy_key`,
`new_key`, `status`, `relevant`, `usage_relevant`, `notes`,
`where_used_in_page`). That row set is the contract. For the new language,
write one row per `en` row, same key columns, same metadata columns,
different `language` and (only) different value columns. **The `en` and
new-language row counts for every db MUST be identical after the run.** If
they aren't, the run is wrong — do not report it as done.

---

## 2. MUST NOT call the original per-type audit scripts' CLI/`main()` against a populated db

**What went wrong the second time:** `audit_home.py`, `audit_blog.py`, and
`audit_legal_bundle.py` each start their `main()` with:

```python
if db_path.exists():
    db_path.unlink()          # <-- deletes the ENTIRE FILE
...
conn.execute("DELETE FROM mapping_audit WHERE puzzle_slug = ?")  # no language filter
```

Running any of these three with `--language ar` against a db that already
held `en` rows **deleted the `en` rows** (or the whole file), because
neither the file-unlink nor the per-slug delete is scoped by language.
`audit_single_puzzle.py` is safer (its delete is scoped to
`puzzle_slug AND language`) but still regenerates rows from scratch, which
violates rule 1.

**Rule:** Never invoke `audit_home.py`, `audit_blog.py`,
`audit_legal_bundle.py`, or `audit_single_puzzle.py`'s CLI for a new
language against an existing db. Only `clone_en_to_language.py` may write to
these files for a new-language population, and it only ever executes:

```sql
DELETE FROM mapping_audit WHERE language = ?   -- scoped, nothing else
INSERT INTO mapping_audit (...) VALUES (...)   -- new rows only
```

If you need those scripts at all, import their `build_rows`/`convert_entry`
/`migrate_page`/`migrate_blog_entry` helpers as pure functions — never call
their `main()`.

**Before running anything the first time for a language, copy the whole
`generator/mapping-check/*.db` set aside** (e.g. to a dated backup folder,
same pattern as `en-backup/`). If a run goes wrong, you restore from that
copy, not from memory.

---

## 3. MUST NOT fabricate a value

If the target language's real prod content doesn't have a field, **leave
both `Legacy_value_by_key` and `new_value` empty.** Do not:
- machine-translate the English value into the empty slot,
- copy the English value in as a placeholder,
- guess based on the field name,
- leave it empty *and* mark it OK — the cloned `status`/`relevant` columns
  came from `en`'s audit and describe `en`'s data, not the new language's;
  that mismatch is expected and fine, don't try to "fix" it by faking data
  instead.

An empty cell is the correct, honest signal that this content doesn't exist
yet for that language. Report empty counts to whoever asked — don't hide
them by filling gaps with junk.

**Exception — only when the value is independently verified in code, not
content:** a small number of `home.db` header fields
(`header.title`/`header.og.title`/`header.meta_description`/
`header.og.description`) are not sourced from any JSON content file at
all — they come from `dot-to-dot-web/lib/localized-seo.ts`'s
`localizedSiteSeo(locale)` function, read by
`app/[locale]/layout.tsx`'s `generateMetadata()`. For these specific four
fields only:
1. Open `lib/localized-seo.ts`, find `localizedSiteSeo`, and check whether
   an `is<Language>(locale)` branch exists for your target language.
2. If yes: copy `title`/`ogTitle`/`description` **verbatim** into
   `clone_en_to_language.py`'s `LOCALIZED_HOME_SEO` dict for that language
   code, citing the function you read it from.
3. If no: leave the English literal in place (this is what
   `clone_en_to_language.py` already does automatically for any language
   without a `LOCALIZED_HOME_SEO` entry) — this is *correct*, verified by
   reading `layout.tsx`: `arabicSeo?.title ?? '<english literal>'` falls
   back to the English string for exactly this case. It is not a gap to
   fill in.

Do not extend this exception to any other field. Every other field's value
must come from an actual content JSON file for that language.

---

## 4. MUST NOT touch prod content

Every script in this process is read-only against
`dot-to-dot-web/content/**` and `dot-to-dot-web/lib/**`. Never write back
into any prod JSON or TS file. The only writes are `INSERT`/`DELETE` into
the throwaway `mapping_audit_*.db` sqlite files under
`generator/mapping-check/`.

---

## 5. MUST scope every write by `language`

Every `DELETE` and every `INSERT` must include the target language
explicitly. Never `DELETE FROM mapping_audit` without a `WHERE language = ?`
clause. Never assume a table only contains one language's rows.

## 9. Verification checklist — run after every language population

1. **Row counts match `en` exactly**, per db:
   ```sql
   SELECT language, COUNT(*) FROM mapping_audit GROUP BY language;
   ```
   `en` and the new language must show identical counts in every db that
   was populated (tables intentionally skipped per rule 6, like a missing
   `usa-250` source, are the only allowed exception — and that must be
   reported, not silently skipped).
2. **`en` rows are still intact** — spot check counts against what they
   were before the run started. If they dropped, you hit rule 2's failure
   mode; restore from backup and re-run through `clone_en_to_language.py`
   only.
3. **Report the empty-value count/percentage per db** to whoever asked —
   don't just say "done." Flag any table with an unusually high empty rate
   (it usually means that category/page genuinely has thin content in that
   language in prod, which is useful information, not a bug to paper over).
4. Do this for every `--dry-run` first, read the output, *then* run for
   real without `--dry-run`.

## 10. How to run it

```bash
cd generator/mapping-check

# 1. The real run automatically backs up every *.db beside this directory.
#    To use a non-sibling prod checkout, pass --web-root /path/to/dot-to-dot-web
#    or set DOT_TO_DOT_WEB_ROOT.

# 2. Dry run — read the output, sanity check filled/blank ratios per table.
python clone_en_to_language.py <lang> --dry-run

# 3. Real run.
python clone_en_to_language.py <lang>

# 4. Verify (rule 9).
python -c "
import sqlite3, glob
for f in sorted(glob.glob('mapping_audit_*.db')):
    conn = sqlite3.connect(f)
    try:
        print(f, conn.execute('SELECT language, COUNT(*) FROM mapping_audit GROUP BY language').fetchall())
    except Exception as e:
        print(f, 'ERR', e)
"
```

To re-run a subset (e.g. after fixing one table's logic):
```bash
python clone_en_to_language.py <lang> --only home,legal
```

## 11. If you think you need to deviate from this file

You don't. If the existing approach genuinely can't handle something new
(a table shape not covered above, a language with a totally different
content structure), stop and say so explicitly instead of improvising —
update `clone_en_to_language.py` and this document together, in the same
change, so the next language benefits from the fix instead of hitting the
same undocumented edge case blind.
